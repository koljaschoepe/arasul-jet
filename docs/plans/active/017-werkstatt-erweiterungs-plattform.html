§1Warum & Ziel ▶ Kurz: Aus dem Terminal-Bereich wird die Bau-Plattform, die Arasul verkauft: sicher bauen, sichtbar verwalten, wirklich anbinden.

Arasul verspricht: Ein technikaffiner Admin beim Kunden baut mit externen Coding-Agents (Claude Code, Codex) — oder dem lokalen Coder — Erweiterungen auf der lokalen Basis: interne Tools, Dashboards, Automatisierungen. Die Logik dafür existiert (Sandboxes, Paketformat, Watcher, Register), aber drei Dinge halten das Versprechen auf:

  • Die Brücke fehlt. Eine live geschaltete App läuft in einem komplett abgeriegelten iframe und kann weder das lokale LLM noch RAG, Dateien oder n8n ansprechen. Die im Manifest deklarierte Zugriffsstufe hat zur Laufzeit keine Wirkung.
  • Die Verwaltung fehlt. Es gibt nur einen Freitext-Ordner + „Erweiterung live schalten“ (Rocket-Button). Was gebaut ist, was live ist, was abgelehnt wurde und warum — all das weiß das Backend, aber die UI zeigt es nicht.
  • Der Alltag hakt. Sitzungen heißen stur „Sitzung N“ und sind nicht umbenennbar, der Kopfbereich stapelt drei Ebenen, Projekte sind pro Account versteckt statt geräteweit sichtbar, der Claude-OAuth-Link ist nicht klick-/kopierbar, und drei bekannte Robustheits-Bugs nagen am Vertrauen.

Fertig heißt: Ein Admin legt ein Projekt an (Zugriffsstufe pro Projekt wählbar), baut mit seinem bevorzugten Agenten per /plan → /execute eine Erweiterung, sieht sie im Werkstatt-Panel mit Status, schaltet sie mit einer klaren Fähigkeiten-Freigabe live — und die App nutzt danach nachweislich LLM, RAG, Dateien und n8n-Flows der lokalen Basis. Sitzungen sind benannt und umbenennbar, jeder am Gerät sieht alle Projekte, ein kaputter Stand ist einen Klick vom Rollback entfernt.

§2Scope ▶ Kurz: Terminal-UX + Erweiterungs-Verwaltung + KI-Brücke + Verbindungen; kein eigenes Internet-Hosting, kein Rollenmodell, kein Marktplatz.

Im Scope

  • Geräteweite Sandbox-Projekte (alle sehen & öffnen alles) + Anwesenheits-Anzeige an Sitzungen
  • 3 Robustheits-Fixes: Bauen-Slug-Prüfung, Doppel-Start-Race, tote Sitzungs-Zeilen nach Crash
  • KI-Brücke: Manifest-Fähigkeiten, kurzlebige gescopte Tokens, Endpunkte für LLM, RAG, Dateien, n8n-Flows + kleines Client-SDK
  • Fähigkeiten-Freigabe beim Live-Schalten („Diese Erweiterung darf: …“)
  • Flow-Erweiterungen: Live schalten = n8n-Import + Aktivierung, Statusanzeige, Deaktivieren pausiert
  • Rollback-Netz: genau ein Schritt zurück (Paket + ggf. n8n-Workflow)
  • Werkstatt-Inventar-API + Werkstatt-Panel (Liste, Status, Aktionen, Ablehnungsgründe; Bausteine-Optik)
  • Projekt-Verbindungen: verschlüsselter Tresor + MCP-Einträge, Injektion als Env + .mcp.json/Codex-Konfig
  • Einzeilige Terminal-Kopfzeile; Sitzungen mit Auto-Namen + serverseitigem Umbenennen
  • KI-Zugangs-Hub (Claude/Codex/Gemini/lokaler Coder) + OAuth-Link-Fix (klickbar, kopierbar)
  • Agenten-Paket in der Werkstatt: /plan, /execute, kleiner /info + geräteneutrale Kontextdateien
  • Doku-Sync (EXTENSIONS, WORKSPACE, API_REFERENCE, DATABASE_SCHEMA, ENVIRONMENT_VARIABLES)

Nicht im Scope

  • Eigenes Internet-Hosting von Erweiterungen (keine Traefik-Dynamik, keine Subdomains) — nach außen gerichtete Projekte werden extern gehostet und von hier nur gemanagt
  • Rollen-/Rechtemodell — Einzel-Admin-Modell bleibt („jeder darf alles“)
  • Öffentlicher Marktplatz / Fremd-Uploads
  • Versions-Historie über den einen Rollback-Schritt hinaus
  • DGX-Spark-/Server-Portierung (nur: Kontextdateien werden geräteneutral formuliert)
  • open-ara-TUI-Politur (Quellen liegen nicht im Repo)
  • Eigene Laufzeit-Container pro Erweiterung
§3Architektur — einfach erklärt ▶ Kurz: Der Werkstatt-Kreislauf bleibt; neu sind Brücke (gescopter Zugriff auf Dienste), Verbindungs-Tresor und ein Inventar, das die UI speist.

Der bestehende Kreislauf bleibt unangetastet: In einer Sandbox (Projekt mit wählbarer Zugriffsstufe) baut ein Agent eine Erweiterung, der Watcher erkennt und registriert sie, der Admin schaltet sie live, und Apps laufen als iframe im Dashboard. Drei Bausteine kommen dazu.

Die Brücke. Das Manifest deklariert künftig konkrete Fähigkeiten (llm, rag, dateien, flows). Beim Live-Schalten bestätigt der Admin diese Liste einmal — wie App-Berechtigungen. Das Dashboard reicht der App per postMessage einen kurzlebigen, exakt auf diese Fähigkeiten gescopten Token; damit ruft sie /api/extensions/:id/bruecke/… auf. Das Backend prüft bei jedem Aufruf Token, Erweiterung und Fähigkeit — alles andere wird abgelehnt. Das abgeriegelte iframe bleibt (die App kommt weiterhin nicht an Cookies oder fremde APIs), nur die Brücken-Routen akzeptieren den Token. Ein Env-Flag kann die Brücke geräteweit abschalten.

Verbindungen & Flows. Pro Projekt lassen sich externe Zugänge (Supabase, Vercel, …) und MCP-Server hinterlegen — Werte landen verschlüsselt im bestehenden Tresor-Muster und werden beim Sandbox-Start als Env-Variablen plus generierter .mcp.json/Codex-Konfiguration injiziert. So kann der Coding-Agent extern gehostete Systeme von hier aus mitverwalten, ohne dass Klartext-Secrets im Workspace liegen. Flow-Erweiterungen werden beim Live-Schalten per n8n-API importiert und aktiviert; ihre Karte zeigt den echten n8n-Status. Jedes Überschreiben sichert den vorherigen Stand als Rollback-Punkt.

§4Umsetzungsschritte ▶ Kurz: 9 Schritte, Fundament zuerst (Backend 1–5), dann UI (6–8), zum Schluss Agenten-Paket + Doku (9). Jeder Schritt lässt das System lauffähig.

Schritt 1 — Geräteweite Projekte + Robustheit Risiko: mittel

Sandbox-Projekte werden geräteweit: Besitz-Filter in listProjects/getProject/loadWorkspace fällt weg (Anzeige „erstellt von“ bleibt), WS-Tickets bleiben nutzergebunden. Anwesenheit: das Backend weiß über activeSessions, wer verbunden ist, und liefert es je Projekt/Sitzung aus. Dazu die drei Robustheits-Fixes: POST /extensions/bauen validiert, dass der Slug eine existierende Werkstatt-Sandbox ist; Container-Start wird atomar (Status-Wechsel per bedingtem UPDATE … RETURNING, kein Doppel-Start-409 mehr); beim Backend-Boot werden verwaiste active-Sitzungs-Zeilen geschlossen (vorhandene SQL-Funktion endlich aufrufen).

§5Akzeptanzkriterien ▶ Kurz: 14 konkret prüfbare Kriterien — von „Sitzung umbenennbar in jedem Browser“ bis „Brücke lehnt nicht freigegebene Fähigkeit mit 403 ab“.
  • Zwei Browser (oder zwei Accounts) sehen dieselbe geräteweite Projektliste; an einer offenen Sitzung ist sichtbar, dass jemand anderes verbunden ist.
  • Doppelklick „Start“ auf dasselbe Projekt erzeugt keinen error-Status mehr; nach einem Backend-Neustart existieren keine aktiven Geister-Sitzungen in der DB.
  • POST /api/extensions/bauen mit nicht existentem oder Nicht-Werkstatt-Slug wird mit Validierungsfehler abgelehnt.
  • Der Terminal-Kopf ist genau eine Zeile (Projekt-Dropdown + Sitzungs-Tabs); die alte große Projektzeile ist weg; Statusleiste zeigt Netz-Modus + Verbindung.
  • Eine per Quick-Launch „Claude Code“ gestartete Sitzung heißt automatisch „Claude Code“; Umbenennen per Doppelklick funktioniert und der Name erscheint identisch in einem zweiten Browser.
  • Das Werkstatt-Panel listet alle erkannten Erweiterungs-Ordner mit Status und Ablehnungsgrund; Rocket-/Hammer-Icons und das Freitext-Ordnerfeld existieren nicht mehr.
  • Live-Schalten einer Erweiterung mit deklarierten Fähigkeiten zeigt den Freigabe-Dialog; ohne Freigabe liefert jeder Brücken-Aufruf 403.
  • Eine Beispiel-App-Erweiterung ruft über die Brücke nachweislich LLM (gestreamt) und RAG auf und zeigt die Antworten im iframe; eine nicht freigegebene Fähigkeit wird serverseitig abgelehnt.
  • Eine Flow-Erweiterung wird beim Live-Schalten in n8n importiert und aktiviert; die Karte zeigt den n8n-Status; Deaktivieren pausiert den Workflow.
  • Nach einem Überschreiben stellt „Rollback“ den vorherigen Stand wieder her (App-Paket bzw. n8n-Workflow) — genau ein Schritt zurück.
  • Eine Projekt-Verbindung (z. B. Supabase-MCP) ist nach Sandbox-Neustart als Env-Variable + Eintrag in .mcp.json in der Sandbox nutzbar; der Klartext-Wert taucht weder in DB-Zeilen, Logs, ps-Ausgabe noch im Workspace auf.
  • Im KI-Zugangs-Hub ist die Claude-Authorize-URL klickbar und kopierbar (auch bei nicht vertrautem Zertifikat); Codex zeigt seinen Anmelde-Status; „Codex anmelden“ ist aus dem Quick-Launch verschwunden.
  • In einer frischen Werkstatt-Sandbox stellt /plan im Claude-Code-Terminal Rückfragen und erzeugt eine HTML-Plandatei; /execute arbeitet sie ab; das Pendant ist für Codex dokumentiert.
  • ./scripts/test/run-tests.sh --all ist grün; die fünf Doku-Dateien sind synchron (Stichprobe: neue Endpunkte in API_REFERENCE, neue Tabellen in DATABASE_SCHEMA, neue Env-Vars in ENVIRONMENT_VARIABLES).
§6Verifikation auf dem Jetson ▶ Kurz: Jede Phase live im echten Browser auf https://192.168.0.197; Brücke zusätzlich per curl-Negativtest; OAuth mit genau einem kontrollierten Versuch.

Nach jedem Phasen-Deploy (docker compose up -d --build der betroffenen Services) wird im echten Browser auf https://192.168.0.197 verifiziert (Zertifikats-/Login-Rezept aus dem Memory-Bestand):

  • Terminal-Flows: Projekt anlegen (Zugriffsstufe wählen) → Sitzung starten → Quick-Launch „Lokaler Coder“ → Auto-Name prüfen → Sitzung umbenennen → zweiten Browser öffnen und geräteweite Sichtbarkeit + Anwesenheits-Anzeige prüfen.
  • Werkstatt-Flows: Beispiel-Erweiterung im Panel sichten → live schalten inkl. Freigabe-Dialog → App-Tab öffnet sich → Brücken-Aufrufe (LLM/RAG) liefern sichtbar Ergebnisse → absichtlich kaputtes Manifest bauen → Ablehnungsgrund erscheint im Panel → Überschreiben + Rollback durchspielen.
  • Flow-Erweiterung: live schalten → Workflow erscheint aktiv in n8n → Karte zeigt Status → Deaktivieren pausiert in n8n (Gegenprobe in der n8n-Oberfläche).
  • Verbindungen: Test-Verbindung anlegen → neue Sitzung → Env-Variable und .mcp.json in der Sandbox prüfen → docker logs, DB-Stichprobe und ps auf Klartext-Freiheit prüfen.
  • Brücken-Härtung: per curl ohne Token, mit abgelaufenem Token und mit nicht freigegebener Fähigkeit → jeweils 401/403; Env-Flag aus → Brücke antwortet deaktiviert.
  • OAuth (vorsichtig): erst Link-Klickbarkeit/Kopieren im Hub prüfen (ohne Anmeldung), dann genau ein Ende-zu-Ende-Versuch mit dem Nutzer; bei 429 sofort stoppen und Befund festhalten. Danach claude-Start in der Sandbox gegen 401 prüfen.
  • Gesundheit: docker compose ps (alle healthy), Backend-Logs auf Fehler-Spikes, Watcher-Log-Stichprobe, run-tests.sh --all vor jedem Merge.

Rollback

  • Pro Schritt ein PR — jeder Schritt lässt das System lauffähig; Rückzug = git revert + Rebuild der betroffenen Services.
  • Migrationen additiv (neue Tabelle, neue Spalten, keine Drops) — ein Code-Rollback läuft gegen das erweiterte Schema weiter; Down-Pfad je Migration dokumentiert.
  • Brücke: Env-Flag deaktiviert alle Brücken-Routen sofort, ohne Redeploy der Erweiterungen.
  • Erweiterungen: das vorher-Paket ist selbst der Produkt-Rollback; bei Flow-Erweiterungen inklusive n8n-Reimport.
  • Geräteweites Modell: reine Code-Änderung (Filter), kein Datenverlust — revertierbar ohne Migration.
