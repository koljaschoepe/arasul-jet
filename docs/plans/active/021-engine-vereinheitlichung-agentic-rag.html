§1Warum & Ziel ▶ Kurz: Eine Engine, ein Top-Coder, agentic RAG — kein Vektor-Ballast mehr auf 64 GB.

Arasul soll ein exzellenter, lokaler Coding-Agent werden: ein Orchestrator, der über Stunden und Tage autonom an großen, komplexen Aufgaben arbeitet, Subagenten spawnt und sehr lange Dokumente/Code stückweise zusammensetzt und aktualisiert — vergleichbar mit dem, wie Claude Code große Aufgaben stemmt. Das läuft asynchron: man stößt einen Lauf an, er arbeitet durch.

Für diesen Workload gilt: Parallelität ist kein Kaufgrund (meist ein Agent gleichzeitig), aber langer Kontext, Toolcall-Zuverlässigkeit und Speicher-Disziplin entscheiden über Erfolg. Genau deshalb ist der reflexhafte Umstieg „alles auf vLLM" für den Orin falsch: das Wunschmodell Qwen3.8-27B braucht dort eine Engine-Version, die der Orin (JetPack 6, vLLM ~0.10.2) heute nicht fährt — nur der GGUF-Weg über Ollama/llama.cpp bringt es auf dem Orin zum Laufen. Auf Thor/x86 dagegen spielt vLLM seine Stärken (native FP8/NVFP4, Ökosystem, Context-Engineering) voll aus.

Gleichzeitig kostet das klassische RAG (Qdrant-Vektor-DB + Embedding-Service) dauerhaft Speicher und einen ganzen Wartungs-Stack — Speicher, den der Coder auf 64 GB besser gebraucht. Für Code navigiert ein Agent mit grep + Symbolindex ohnehin gezielter als semantische Vektor-Suche.

Fertig heißt: Auf dem Orin lädt die Plattform Qwen3.8-27B als Standard-Coder bei Bedarf, entlädt ihn im Leerlauf, und ein Agent löst eine mehrstufige Coding-Aufgabe gegen ein echtes Repo allein über grep + Symbolindex + Datei-Werkzeuge — ganz ohne Qdrant. Die Engine-Wahl folgt automatisch der erkannten Hardware (Orin → Ollama, Thor/x86 → vLLM), der vLLM-Pfad ist auf dem Orin dev-verifiziert, und Qdrant + Embedding-Service sind entfernt, ohne die Dokument-/OCR-Funktion zu zerstören.

§2Scope ▶ Kurz: Engine-Routing + Gateway + Qwen3.8-27B + agentic RAG in einem Plan; RAG-Entfernung zuletzt.

Im Scope

  • Engine-Routing über die HAL: config/platforms/* → Orin=Ollama, Thor/x86=vLLM, mit manuellem Override.
  • Vereinheitlichung der HW-Klassifizierung auf eine Quelle (config/platforms), Ablösung der SGLang-Wahl aus Plan 020.
  • Modell-Gateway im Backend: eine /models-Sicht, zwei Backends (Ollama nativ / vLLM start-stop-on-idle).
  • Qwen3.8-27B als Standard-Coder (GGUF via Ollama), altes MoE umschaltbar; Toolcalls per erzwungenem Format/Grammatik.
  • Agentic RAG: gehärtete grep-Suche + neuer Tree-sitter/ctags-Symbolindex als Agent-Werkzeuge.
  • Dokument-Feature auf agentisch umstellen (Upload = Datei im Projektordner + OCR-Textlayer, Agent liest/grept gezielt).
  • vLLM-Engine-Tier: Compose-Service + Gateway-Anbindung, dev-verifiziert auf dem Orin-vLLM (Integrationsnachweis).
  • Klassisches RAG entfernen (Qdrant + Embedding-Service + Vektor-Pfad) — letzter, rückrollbarer Schritt.

Nicht im Scope

  • Echte Thor-/DGX-Hardware-Abnahme (kein Gerät da) — getrackter Folge-Plan, gekoppelt an die HAL.
  • SGLang (durch vLLM ersetzt; kein zweiter Server-Engine-Track).
  • Neues Chat-/Agenten-UI (bleibt wie in Plan 019); nur Modell-Auswahl + RAG-Einstellungen werden berührt.
  • Multi-User/Rollen (es bleibt Einzel-Admin).
  • Löschen der Postgres-Tabellen documents/document_chunks (tragen den OCR-Textlayer — bleiben erhalten).
  • Speculative Decoding / EAGLE-Feintuning (später auf Thor, wo es zählt).
§3Architektur — einfach erklärt ▶ Kurz: Frontend → ein Modell-Gateway → HW-passende Engine; Agent sucht per grep/Symbol statt Vektor-DB.

Was ändert sich am System und warum so? Heute spricht das Backend fest mit Ollama, und der RAG-Pfad schickt jede Frage durch Embedding → Qdrant. Das ist an ein Gerät und an eine Engine gebunden und trägt die Vektor-DB als Dauerlast mit.

Neu schiebt sich ein dünnes Modell-Gateway dazwischen: das Frontend sieht weiterhin nur eine /models-Schnittstelle, dahinter wählt das Gateway anhand der erkannten Hardware die Engine. Auf dem Orin ist das Ollama (das entlädt Modelle schon heute nutzungsabhängig über die adaptive Keep-Alive-Logik). Auf Thor/x86 startet das Gateway bei Bedarf den vLLM-Container und stoppt ihn nach Leerlauf — beides über denselben GPU-Lock, damit nie zwei Verbraucher gleichzeitig auf die GPU gehen.

Der zweite Umbau betrifft das Wissen: statt semantischer Vektor-Suche bekommt der Agent direkte Werkzeuge — eine gehärtete grep-Suche (die es als dateien_suchen schon gibt) plus einen neuen Symbolindex (Tree-sitter/ctags), der Funktionen, Klassen und Referenzen als navigierbare Karte liefert. Hochgeladene Dokumente landen als Dateien im Projektordner (mit OCR-Textlayer in Postgres) und werden vom Agenten gezielt gelesen — kein Qdrant mehr nötig. Alle Datei-Werkzeuge gehen weiter zwingend durch die Symlink-sichere Pfadprüfung.

Jeder Schritt ist ein eigener PR mit code-reviewer-Gate; Deploy-Rollback per Branch-Restore auf dem Gerät.
