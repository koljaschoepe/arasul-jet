§1Warum & Ziel ▶ Kurz: Chat so nachvollziehbar wie Claude Code/Cursor + drei reale Datei-Bugs weg.

Das Chat-Interface ist heute schwer zu folgen: Gedankengang, „arbeitet", Plan-Erstellung und die abgeleiteten Aufgaben erscheinen gleichzeitig und an wechselnden Stellen — oben stehen die Aufgaben, unten wird geschrieben, dazwischen rauscht ein flacher Strom aus „listet/liest/sucht"-Zeilen durch, ohne dass man sieht, was bei einem Schritt herauskam oder dass der Agent überhaupt noch arbeitet.

Vorbild sind Claude Code und Cursor: eine feste Aufgabenliste, die sich Stück für Stück abhakt; die einzelnen Arbeitsschritte sauber unter der jeweiligen Aufgabe gruppiert und aufklappbar mit Ergebnis; Subagenten als eigene, verschachtelte Blöcke; und ein deutliches „lebt noch"-Signal. Parallel behebt der Plan drei Dinge, die beim Testen real gestört haben: (1) der Agent hat trotz angehängtem Kundenordner in / gesucht und Dateien nicht gefunden, (2) eine 11,5-MB-Bild-PDF ließ sich im Editor nicht anschauen und der Agent konnte sie nicht lesen, (3) die Indexierung dieser Bild-PDF ist fehlgeschlagen.

Fertig heißt: Man kann dem Agenten im Chat mühelos folgen — Aufgabenliste unten hakt sich ab, jeder Schritt zeigt sein Ergebnis, Subagenten sind aufklappbar, ein Puls zeigt „arbeitet noch"; der Agent arbeitet ausschließlich im angehängten Ordner; große PDFs/Bilder lassen sich anschauen und der Agent kann sie (per OCR) lesen; die Bild-PDF indexiert grün.

§2Scope ▶ Kurz: Chat-Darstellung + Protokoll + 4 Bugfixes; kein Umbau der Modelle/RAG-Qualität.

Im Scope

  • Neues, typisiertes Chat-Ereignis-Protokoll (task/step/agent) auf Basis des vorhandenen Schritt-Baums.
  • Neue Chat-Darstellung: feste Todo-Leiste unten, Gruppierung unter Aufgaben, verschachtelte Subagenten, Puls + aktive Zeile, Ergebnis-Kurzfassung je Schritt + „mehr anzeigen", erledigte Aufgaben klappen ein.
  • Strenge Ordner-Bindung der Agent-Werkzeuge (Datei- und Terminal-Werkzeug) an den angehängten Ordner / das aktive Projekt.
  • PDF-Viewer (blättern) + Bild-Viewer (zoom) im Workspace, gestreamt bis ~50 MB.
  • OCR-Lesepfad für bildbasierte PDFs (Indexer) + Behebung der fehlgeschlagenen Indexierung (poppler/OCR-Engine bereitstellen).
  • Chunked/seitenweises Lesen großer Dateien durch den Agenten.
  • Aggressivere Subagenten-Delegation mit eigenem Kontextbudget.

Nicht im Scope

  • Kein Umbau der Modell-Qualität, der RAG-Trefferlogik oder der Embeddings.
  • Kein neues Rechte-/Rollenmodell (Einzel-Admin bleibt).
  • Keine Änderung an der Projekt-Vereinheitlichung aus Plan 018 (aktives Projekt bleibt die Wahrheit).
  • Kein Editor für PDFs/Bilder (nur Ansehen), kein Multi-Format-Konverter.
  • Kein Fallback auf die alte Chat-Darstellung (bewusst entfernt).
  • Keine neue Chat-History-/Persistenz-Migration, sofern nicht technisch nötig.
§3Architektur — einfach erklärt ▶ Kurz: Vorhandenen Schritt-Baum um eine Aufgaben-Ebene + Ergebnisse erweitern, Darstellung neu bauen.

Der Chat ist heute schon ein Agent mit Werkzeugschleife: Das Backend (chatAgentRunner.js) sendet über einen Live-Stream (SSE) Ereignisse — „Schritt gestartet", „Schritt fertig", „Todos aktualisiert", „Text-Token" — und trägt Schritte bereits als Baum mit Eltern/Kind-Beziehung. Das Frontend (ChatContext.tsx → CompactMessage.tsx) rendert diesen Baum. Wir werfen diesen Transport also nicht weg, sondern erweitern ihn: Wir führen eine oberste Aufgaben-Ebene ein (jede Todo ist ein Baum-Elternknoten), hängen an jeden fertigen Schritt eine Ergebnis-Kurzfassung, und geben Subagenten einen eigenen Elternknoten. Auf dieser sauberen Datenbasis bauen wir die Darstellung komplett neu (feste Todo-Leiste unten, Gruppierung, Verschachtelung, Puls).

Weil es keinen Fallback geben soll, ist die Reihenfolge des Ausrollens entscheidend: Backend und Frontend gehen in einem Deploy live (der Jetson deployt das ganze Repo auf einmal), damit nie eine neue Darstellung auf altes Protokoll (oder umgekehrt) trifft. Die Ereignis-Namen bleiben abwärts-lesbar, wo möglich, damit ein während des Deploys laufender Chat nicht hart abbricht.

Die Datei-Themen sind entkoppelt: Die Ordner-Bindung sitzt an der einen Stelle, über die alle Datei-Werkzeuge laufen (pathSafe.resolveRealWithinRoots) — der angehängte Ordner wird zur Wurzel; das bisher ungeschützte Terminal-Werkzeug bekommt dieselbe Bindung. Der Viewer bekommt einen eigenen gestreamten Endpunkt (nicht das 5-MB-gedeckelte Editor-JSON). OCR ist heute faktisch tot (im Indexer-Dockerfile fehlen poppler-utils und eine OCR-Engine, Fehler werden still verschluckt) — das wird provisioniert und der Fehler sichtbar gemacht.

§4Umsetzungsschritte ▶ Kurz: 5 Phasen — jede lässt das System lauffähig, jede wird live geprüft.

Phase 2 — Angehängter Ordner ist die Wurzel Risiko: mittel

Der angehängte Ordner (bzw. das aktive Projekt) wird zur Wurzel der Agent-Werkzeuge; Pfade relativ dazu, listet "." zeigt den angehängten Ordner, kein ungefragtes Ausbrechen nach /. Die Datei-Werkzeuge laufen bereits über pathSafe.resolveRealWithinRoots — sicherstellen, dass die Wurzel korrekt aus dem angehängten Ordner abgeleitet wird (nicht das ganze Projekt-Ablage-Root). Das Terminal-Werkzeug (heute ohne eigenes Path-Sandboxing) an denselben Ordner binden (cwd + Mount-Scope). Zuerst live reproduzieren, dann fixen. Regressionstests für Wurzel-Ableitung ergänzen (fehlen heute komplett).

Phase 4 — OCR + große Dateien lesen + Indexierungs-Bug Risiko: hoch

Ursache der fehlgeschlagenen Indexierung ist die fehlende OCR-Infrastruktur: poppler-utils und eine OCR-Engine fehlen im Indexer-Image, Fehler werden still verschluckt. Beheben: poppler-utils ins document-indexer/Dockerfile, eine OCR-Engine (Tesseract, ARM64-tauglich) bereitstellen, ocr_pdf_* tatsächlich funktionsfähig machen und Indexierungsfehler nicht mehr still schlucken (sichtbar melden). Bild-PDF re-indexiert grün. Agent-Lesepfad: große Textdateien seitenweise/chunked lesen (eigener Lesepfad, nicht das 5-MB-Editor-Limit), bildbasierte PDFs über denselben OCR-Weg in Text wandeln, damit der Agent sie lesen kann.

Ergebnis (Kern-Fix; „grün"-Nachweis nach Deploy): Ursache bestätigt — OCR lief bisher nur über separate HTTP-Sidecars (tesseract:8085/paddleocr:8086), die auf dem Gerät nicht laufen → Bild-PDFs indexierten still leer. Fix: selbst-enthaltene lokale OCR — poppler-utils + tesseract-ocr(+deu/eng) ins Indexer-Image, pytesseract als Dependency, ocr_service bevorzugt eine lokale Engine (get_available_ocr_engine → „local", ocr_image nutzt pytesseract.image_to_string) — HTTP-Sidecars bleiben optionaler Fallback. Fehler werden nicht mehr verschluckt: eine bildbasierte PDF ohne OCR-Text loggt jetzt WARNING/ERROR statt still leer zu indexieren. Agent-Lesepfad: dateien_lesen liest große Dateien chunked per neuem offset-Parameter (fenstriges Lesen, nennt den nächsten offset) — jenseits des 5-MB-Editor-Limits, mit Kontextschutz je Block. Tests: flowTools 56 (chunked/offset + Byte-Deckel) grün; py_compile der Indexer-Module ok; eslint sauber. Live verifiziert (Jetson, PR #331 · e63c836): im Indexer-Container tesseract 5.3.0 + pdftoppm (poppler) vorhanden; On-Device-Smoke gegen das eigene Modul: ocr_service.get_available_ocr_engine() → „local", ocr_image() auf ein Text-Bild → ok=True, engine=local, text≈"Arasul Hackathon 2026". Die lokale OCR extrahiert also echt Text — der Bild-PDF-Indexpfad (poppler-Rasterung → lokale OCR) ist damit funktionsfähig.

Phase 5 — Subagenten für kleine Aufgabenblöcke Risiko: mittel

Orchestrierung so anpassen, dass größere Teilaufgaben automatisch an frische Subagenten mit eigenem Kontextbudget delegiert werden; der Hauptchat bleibt schlank und bekommt nur die Ergebnisse zurück (verhindert Kontextüberlauf bei komplexen Aufgaben). Die verschachtelte Darstellung dafür kommt aus Phase 1. Budget/Limits sauber setzen, damit keine Endlos-Schachtelung entsteht.

chatAgentRunner.js (Delegations-Anweisung + Budget-Verdrahtung) · agentConfig.js (MAX_SUBAGENTEN) · docs/ENVIRONMENT_VARIABLES.md · Tests: agentConfig.test.js, subagent.test.js

Ergebnis: Die Architektur trug „schlank durch Delegation" schon (Subagent = eigener frischer Kontext, nur das Vertrags-Ergebnis kommt zurück; Roh-Ausgabe bleibt in raw_output). Verstärkt wurde das Verhalten: Regel 7 der Orchestrator-Anweisung fordert jetzt AGGRESSIVE Delegation — jeden mehrschrittigen/leselastigen Teilblock an einen frischen Subagenten geben, unabhängige Blöcke als getrennte Aufrufe, „viele kleine statt ein überladener Eigen-Lauf". Das Subagent-Budget ist konfigurierbar (agentConfig.MAX_SUBAGENTEN, Standard 60 statt fix 40, env AGENT_MAX_SUBAGENTEN) und in RunLimits verdrahtet; die Verschachtelung bleibt über maxTiefe=2 hart begrenzt (keine Endlos-Schachtelung — in subagent.test.js abgedeckt). Tests: agentConfig (Default/Env/NaN-Wächter) + subagent (Zähl-/Tiefen-/Zeit-Bremse) 40 grün; eslint sauber. Das reine Delegations-Verhalten ist modellabhängig und wird nach Deploy per komplexem Chat live gegengeprüft (mehrere sichtbare Subagenten).
§5Akzeptanzkriterien ▶ Kurz: Konkret prüfbar — pro Phase mindestens ein messbares Kriterium.
  • Bei einer mehrschrittigen Aufgabe erscheint unten eine feste Todo-Leiste, die sich live abhakt (z. B. „2/5"); bei einer einfachen Frage bleibt der Chat schlicht ohne Todo-Leiste.
  • Arbeitsschritte sind unter der jeweiligen Aufgabe gruppiert und aufklappbar; jeder fertige Schritt zeigt eine Ergebnis-Kurzfassung mit „mehr anzeigen" für Details.
  • Subagenten erscheinen als eigene, verschachtelte, aufklappbare Blöcke mit Rolle/Auftrag + Endergebnis.
  • Während der Agent arbeitet, ist ein pulsierendes Signal und eine animierte aktive Zeile sichtbar; erledigte Aufgaben klappen automatisch zu einer Ergebniszeile ein.
  • Der alte flache Darstellungspfad ist entfernt; kein Fallback im Code.
  • Mit angehängtem Ordner arbeitet der Agent nur darin: listet "." zeigt den angehängten Ordner, Pfade sind relativ dazu, ein Ausbruch nach / passiert nicht (Datei- und Terminal-Werkzeug).
  • Eine PDF > 5 MB und < 50 MB öffnet sich als blätterbarer PDF-Viewer; ein großes Bild öffnet sich im Bild-Viewer mit Zoom.
  • Die zuvor fehlgeschlagene bildbasierte Hackathon-PDF indexiert grün (OCR liefert Text); ein Indexierungsfehler wird künftig sichtbar gemeldet, nicht still verschluckt.
  • Der Agent kann eine große und eine bildbasierte PDF lesen (chunked bzw. via OCR) und im Ergebnis Inhalt daraus zeigen.
  • Bei einer komplexen Aufgabe delegiert der Agent sichtbar an mehrere Subagenten; der Hauptverlauf bleibt schlank.
  • Backend- und Frontend-Tests grün; API_REFERENCE + WORKSPACE-Doku spiegeln das neue Protokoll/Verhalten.

Null neue Console-Fehler. Fehlende Test-Abdeckung für Path-Scoping heute → Regressionen unbemerkt.MittelNeue Regressionstests für Wurzel-Ableitung im selben PR (nicht danach).

Rollback

Jede Phase ist ein eigener, lauffähiger Zustand. Bei Regression: git revert des jeweiligen Squash-Commits über denselben Auto-Merge-Weg; der Deploy rollt bei Fehlschlag automatisch auf den Vorzustand zurück. Keine Schema-Migration geplant (Schritte liegen als JSONB) — sollte Phase 1 doch eine brauchen, ist sie additiv und mit Down-Pfad. Das Indexer-Image ist über den Git-Stand reproduzierbar.
