Was passiert
Das oben gewählte Projekt wird zur einzigen Wahrheit: Dateien, Flows (nur dieses Projekt + globale) und Terminal folgen ihm. Der eigene Projekt-Umschalter im Terminal fällt weg. Die Werkstatt (Erweiterungen) zieht auf eine neue Projekt-Übersichtsseite; davor gibt es eine Projekt-Startseite mit „Zurück".
Warum jetzt
Heute laufen zwei getrennte Projekt-Begriffe nebeneinander — der Explorer zeigt „test", das Terminal „Kunden". Das ergibt keinen Sinn und verwirrt.
Größtes Risiko
Das Terminal ist die meistgenutzte Fläche. Der Umbau seiner Projekt-Herkunft plus eine Migration der offenen Sitzungen kann den Alltag stören, wenn etwas schiefgeht.
Du entscheidest
  • Ein aktives Projekt steuert alles; das Terminal hat keinen eigenen Umschalter mehr.
  • Container werden beim Öffnen automatisch angelegt/gekoppelt (Netz „intern").
  • Werkstatt auf die Projekt-Übersichtsseite; Flows-Sidebar nur aktiv + global.
  • Ein großer Wurf (eine PR); bestehende Container per Namensgleichheit zugeordnet.
§1Warum & Ziel ▶ Kurz: Ein Projekt oben steuert alles — heute driften Explorer und Terminal auseinander.

Im Workspace gibt es aktuell zwei völlig getrennte „Projekt"-Begriffe. Der Explorer und die Flows hängen am Workspace-Projekt (oben in der Menüleiste wählbar). Das Terminal hat einen eigenen Projekt-Umschalter und hängt an einem Sandbox-Container — einer anderen Liste. Beide wissen nichts voneinander. Ergebnis: Man kann links im Projekt „test" arbeiten und rechts im Terminal in „Kunden" sein. Das ist verwirrend und war der Kern deiner Rückmeldung.

Ziel ist eine einzige, oben getroffene Projektauswahl, der alles folgt: die Dateien, die Flows (nur die des aktiven Projekts plus die globalen) und das Terminal. Zusätzlich bekommt jedes Projekt eine Übersichtsseite (Info + Erweiterungen/Werkstatt + Schnellzugriff), erreichbar über eine Projekt-Startseite mit klarem „Zurück". Die Werkstatt verschwindet dafür aus dem Terminal.

Fertig heißt: Ich wähle oben ein Projekt — und Dateien, Flows und Terminal zeigen alle genau dieses Projekt; das Terminal hat keinen zweiten Umschalter mehr; die Werkstatt lebt auf der Projektseite; und ich bewege mich über Liste → Projekt → Übersicht → Arbeiten sauber vor und zurück.

§2Scope ▶ Kurz: Terminal an das aktive Projekt koppeln + Projektseiten; kein Verschmelzen der Datenmodelle.

Im Scope

  • Terminal folgt dem aktiven Workspace-Projekt; eigener Projekt-Umschalter raus.
  • Container beim Öffnen automatisch anlegen/koppeln (über project_id), Netz „intern".
  • Terminal-Sitzungen werden pro Projekt gemerkt.
  • Neue Projekt-Startseite (Kachelliste) + Projekt-Übersichtsseite (Info + Werkstatt + Schnellzugriff), mit „← Projekte"/Breadcrumb.
  • Werkstatt aus dem Terminal auf die Übersichtsseite verschieben.
  • Flows-Sidebar auf aktives Projekt + global scopen.
  • Einmaliger Backfill: bestehende Container per Namensgleichheit einem Projekt zuordnen.

Nicht im Scope

  • Kein Verschmelzen von Workspace- und Sandbox-Projekt zu einer Tabelle (bleibt 1:1-Kopplung).
  • Kein neues Rechte-/Mehrbenutzer-Modell (Einzel-Admin bleibt).
  • Keine Änderung an Chat/RAG-Scoping (folgt bereits dem aktiven Projekt).
  • Keine Idle-Abschaltung/Container-Quoten (nur als Risiko notiert, separater Schritt später).
  • Keine Terminal-interne Rendering-Politur (war Phase A, bereits live: PR #326).
§3Architektur — einfach erklärt ▶ Kurz: Zwei Projekt-Begriffe bleiben, werden aber 1:1 über project_id gekoppelt; das aktive Projekt ist die einzige Wahrheit.

Wir verschmelzen die zwei Datenmodelle bewusst nicht (das wäre ein großer, riskanter Umbau). Stattdessen koppeln wir sie 1:1: Jedes Workspace-Projekt bekommt genau einen Sandbox-Container über das schon vorhandene Feld sandbox_projects.project_id. Die Oberfläche zeigt künftig nur noch Workspace-Projekte; das Terminal schlägt zum aktiven Projekt den gekoppelten Container nach — oder legt ihn beim ersten Öffnen automatisch an (Netz „intern").

Damit wird der obere Projekt-Umschalter (der den Explorer heute schon steuert) zur einzigen Quelle der Wahrheit. Das Terminal verliert seinen zweiten Umschalter und liest ab jetzt dasselbe „aktive Projekt". Offene Terminal-Sitzungen werden pro Projekt gemerkt, damit ein Projektwechsel nichts verwirft.

Neu sind zwei Seiten (als Workspace-Tabs, gebaut nach dem bestehenden Muster der „Kundenübersicht"): eine Projekt-Startseite (Kachelliste aller Projekte) und eine Projekt-Übersichtsseite pro Projekt (Info, die Werkstatt/Erweiterungen — nur wenn welche existieren — und Schnellzugriff zu Terminal/Dateien/Flows). Serverseitig kommt genau ein neuer Baustein dazu: ein Endpunkt, der zu einer Projekt-ID den Container liefert oder atomar anlegt+koppelt.

§4Umsetzungsschritte ▶ Kurz: 6 logische Schritte, aber als EIN großer Wurf ausgeliefert (eine PR, ein Deploy).

Hinweis (deine Entscheidung): Rollout „in einem großen Wurf" — die folgenden Schritte sind die innere Gliederung, werden aber gemeinsam als eine PR / ein Deploy ausgeliefert und zusammen verifiziert.

Schritt 1 — Backend: „ensure-for-project" + Backfill Risiko: Mittel

Neuer Endpunkt, der zu einer Workspace-Projekt-ID den gekoppelten Sandbox-Container liefert oder ihn atomar anlegt+koppelt (nutzt das bestehende sandboxService.createProject(), das project_id + eigenen Wissensraum in einer Transaktion anlegt), Netz-Default „intern". Migration 139 fügt einen partiellen Unique-Index auf sandbox_projects(project_id) hinzu (erzwingt 1:1, entschärft Doppelklick-Race). Zusätzlich ein einmaliger Boot-Backfill-Service, der bestehende ungekoppelte Container per Namensgleichheit einem Projekt zuordnet bzw. via projectService.createProject() ein Projekt anlegt (damit Ordner + DB zusammen entstehen — reines SQL kann den Ordner nicht anlegen).

apps/dashboard-backend/src/routes/sandbox.js · services/sandbox/sandboxService.js · schemas/sandbox.js · services/rag/projectService.js · neuer Backfill-Service (Boot) · services/postgres/init/139_sandbox_project_link.sql

Schritt 2 — Store: per-Projekt-Sitzungen + Tab-Typen Risiko: Mittel

terminalSessions/activeTerminalSessionId werden pro Projekt geführt (Registry je gekoppeltem Container) — inkl. zustand-persist-Migration mit Versionsbump, damit bestehende offene Sitzungen nach dem Deploy weder verloren gehen noch doppelt erscheinen. Neue Workspace-Tab-Typen projekte (Startseite) und projektuebersicht (projektgebunden, ID-parametrisiert) über die vier Touchpoints (Typ-Union · DEFAULT_TITLES · tabId · tabToPath/pathToTabSpec) plus die Verdrahtung in TabContent.

Schritt 3 — Terminal an aktives Projekt koppeln Risiko: Hoch

SandboxApp/TerminalTabs: eigenen Projekt-Umschalter und die eigene Projektliste entfernen; den Container aus useActiveProject().activeId über den ensure-Endpunkt auflösen; beim Öffnen ohne Container automatisch anlegen (Netz „intern"); Sitzungen aus der per-Projekt-Registry rendern. Der fragile Bootstrap-/Auto-Restore-Effekt wird auf die neue Quelle umgestellt. useTerminal bleibt unverändert (nimmt die Container-ID weiterhin als opaken Parameter).

Schritt 4 — Startseite + Übersicht + Werkstatt-Umzug Risiko: Mittel

Neue Projekt-Startseite (Kachelliste aller Projekte, Klick öffnet die Übersicht) und Projekt-Übersichtsseite (Info: Netzmodus/Ablage; Werkstatt-Abschnitt nur wenn Erweiterungen existieren; Schnellzugriff-Buttons Terminal/Dateien/Flows; „← Projekte"-Button + Breadcrumb) — gebaut nach dem Muster von KundenUebersichtTab. §5Akzeptanzkriterien ▶ Kurz: Ein Projekt oben = alles gleich; Terminal ohne eigenen Umschalter; Werkstatt auf der Projektseite.
  • Wähle ich oben ein Projekt, zeigen Explorer, Terminal und Flows dasselbe Projekt — keine „links test / rechts Kunden"-Diskrepanz mehr.
  • Das Terminal hat keinen eigenen Projekt-Umschalter mehr; aus dem Terminal lässt sich kein Projekt „öffnen".
  • Öffne ich das Terminal für ein Projekt ohne Container, wird genau EIN Container automatisch angelegt+gekoppelt (Netz „intern") und das Terminal verbindet.
  • Wechsle ich das aktive Projekt und wieder zurück, sind die vorherigen Terminal-Sitzungen dieses Projekts wieder da (pro Projekt gemerkt).
  • Die „Projekte"-Startseite listet alle Projekte; ein Klick öffnet die Übersichtsseite mit Info + Werkstatt (nur wenn Erweiterungen) + Schnellzugriff; „← Projekte"/Breadcrumb funktioniert.
  • Die Werkstatt erscheint nicht mehr im Terminal.
  • Die Flows-Sidebar zeigt nur die Flows des aktiven Projekts plus die globalen.
  • Nach dem Deploy ist jeder bisher eigenständige Container einem Projekt zugeordnet (Namensgleichheit) — nichts verschwindet.
  • Bereits offene Terminal-Sitzungen überleben den Deploy ohne Verlust oder Duplikate.

Rollback

Ein großer Wurf = eine PR. Rollback per git revert des Squash-Commits über denselben Auto-Merge-Pfad; deploy-local.sh rollt bei einem fehlgeschlagenen Deploy ohnehin automatisch auf den vorherigen Stand zurück. Migration 139 ist additiv (nur ein Index); der Backfill ist idempotent und setzt nur NULL → Wert (Container/Projekte bleiben erhalten, nur die Kopplung entsteht). Die persist-Migration ist versioniert, sodass ein Zurückrollen die alte Registry weiterhin lesen kann.
