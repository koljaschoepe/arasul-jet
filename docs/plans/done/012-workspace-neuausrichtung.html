§1Warum & Ziel ▶ Kurz: Ein Ordner-Kontext als Fundament — darauf ruhige Navigation, Skills als USP und ein Erweiterungs-Baukasten.

Heute besteht die Arbeitsumgebung aus vielen guten Einzelteilen, die aber nicht auf einem gemeinsamen Fundament stehen. Konkret aus dem Ist-Zustand (per Codebase-Recherche belegt):

  • Es gibt keinen „aktiven Ordner". Ordner (knowledge_spaces) und Terminal-Container (sandbox_projects) sind zwei getrennte Welten. Der Chat-Kontext wird heute per Drag&Drop als Multi-Ordner-Set gesetzt — es gibt keine feste, global sichtbare Auswahl „welche Firma ist gerade aktiv".
  • Die Activity-Bar liegt innerhalb der einklappbaren Sidebar. Klappt man die Sidebar ein, verschwindet auch der „Dateien"-Button — nur ⌘B holt sie zurück. Das ist der Kern-Bug, den du beschrieben hast.
  • Die Modell-Filter sitzen mitten im Store-Tab (eine w-52-Leiste im Inhalt), nicht in der echten linken Sidebar. Facetten heute: Fähigkeit/Typ/Größe/Status — „Fähigkeit" soll raus.
  • Skills öffnen ein Fullscreen-Popup; die Preview zeigt nur die erzeugte Markdown-Datei, nicht den echten Prompt, der ans Modell geht. Die /skills-Übersicht ist nur ein Toast-Platzhalter.
  • „Erweiterungen" sind real nur n8n plus ein „kommt bald"-Platzhalter — der versprochene Eigenbau fehlt.
  • Die Indexierung hinterlässt Zombie-Chunks bei geänderten Dokumenten: der saubere „alte Version löschen → neu einfügen"-Mechanismus existiert nur im Workspace-Pfad, nicht im normalen Upload/Scan-Pfad.

Ziel: Ein klares mentales Modell — „alles basiert auf der einen Ordnerstruktur". Ein aktiver Top-Level-Ordner steuert Chat und Suche. Die Navigation folgt dem VS-Code-Marktplatz-Muster (feste Icon-Leiste links, kontextabhängige Sidebar, Inhalt in der Mitte). Skills werden zur zentralen, transparenten Steuer-Oberfläche (der USP: Prozessschritte, Subagenten, Tools). Und obendrauf ein Erweiterungs-Baukasten, mit dem man live im Terminal eigene Apps, n8n-Flows und Tools baut, forkt und herunterlädt — sauber getrennt, damit man langfristig weiter daran bauen kann.

§2Scope ▶ Kurz: Fundament + Navigation + Store + Skills-Zentrale + Erweiterungs-Baukasten + Index/Suche. Kein Rollenmodell, kein OTA.

Im Scope

  • Workspace-Switcher oben in der Shell
  • Feste Activity-Bar herauslösen + ⌘B/„Dateien"-Bug beheben
  • Kontextabhängige Sidebar (Dateien · Suche · Modelle · Erweiterungen · Skills)
  • Modell-Filter aufräumen (Fähigkeit raus), in die Sidebar, ruhiges 3er-Grid, reiche Detailseite
  • Erweiterungen-View neu, mit sinnvollen Filtern + Bugcheck
  • Skill-Editor als Tab (kein Popup) mit Einstellungen + Live-Laufzeit-Prompt
  • Skills-Übersicht als echte Ansicht statt Toast-Stub
  • Erweiterungs-Baukasten: Dev-Sandbox mit Seed-Kontext, Drei-Stufen-Zugriff, Bau-Skills, Fork/Download/Install
  • Indexierung: delete-before-upsert + Content-Hash-Gate + Payload-Indizes; themen-/ordner-optimierte Suche
  • Doku + Tests + saubere Feature-Trennung

Nicht im Scope

  • Rollen-/Rechtekonzept (es bleibt bei einem Admin, der alles darf)
  • OTA-Updates, Netz-Trennung, /healthz (bewusst geparkt)
  • Öffentlicher Erweiterungs-Marktplatz mit Fremd-Uploads (später; hier nur lokaler Bau + Export/Import)
  • Neues Embedding-Modell / Chunking-Grundumbau (nur Robustheit + Scoping, keine Neu-Vektorisierung aller Bestände)
  • Terminal an einen knowledge_space koppeln (bewusst verworfen — Terminal ist die Sandbox-Welt mit Zugriffs-Stufen)
§3Architektur — einfach erklärt ▶ Kurz: Aktiver Ordner oben → Chat+Suche gescoped. Terminal = Sandbox-Welt mit Zugriffs-Stufen → Erweiterungs-Baukasten.

Zwei Welten, sauber getrennt, mit einer klaren Klammer oben:

  • Wissens-Welt (links + Mitte + Chat): Der Dateibaum sind die knowledge_spaces. Genau ein Top-Level-Ordner ist „aktiv" (Switcher oben). Chat und Suche binden standardmäßig an diesen Ordner-Teilbaum; einzelne Dateien lassen sich zusätzlich anheften. Die Suche (Qdrant) filtert über das bereits vorhandene space_id-Payload — das machen wir zum Default statt zum Sonderfall.
  • Sandbox-Welt (rechts, Terminal): Das Terminal ist nicht an einen Wissensordner gekoppelt. Es ist die Umgebung für externe Agenten/Modelle (z. B. Claude Code) und für den Erweiterungs-Bau. Jede Sandbox hat eine von drei klaren Zugriffs-Stufen: nur Internet · genau ein interner Ordner · voller Systemzugriff. Eine spezielle „Werkstatt"-Sandbox ist mit Referenz-/Template-Wissen vorbereitet, sodass zwei Bau-Skills (/erweiterung, /execute) daraus fertige, forkbare, herunterladbare Erweiterungen machen.

§5Akzeptanzkriterien ▶ Kurz: Aktiver Ordner steuert Chat+Suche, Bugs weg, Skills-Tab mit Live-Prompt, Erweiterung baubar, keine Zombie-Chunks.
  • Oben ist ein Workspace-Switcher; Wechsel schaltet sichtbar den Chat- und Such-Kontext um.
  • Chat und Suche liefern standardmäßig nur Treffer aus dem aktiven Ordner; angeheftete Dateien sind immer im Kontext.
  • Die Activity-Bar bleibt sichtbar, auch wenn die Sidebar eingeklappt ist; ein Klick auf „Dateien" bringt den Baum zuverlässig zurück (⌘B und Klick verhalten sich konsistent).
  • Modell-Filter zeigen nur Typ/Größe/Status (keine „Fähigkeit") und sitzen in der linken Sidebar; das Grid ist ruhig (Standard 3 pro Reihe) und sinnvoll vorsortiert.
  • Die Modell-Detailseite ist mit Karten gefüllt (Specs, Hardware-Fit, Einsatzzwecke, verwandte Modelle, Aktionen) und wirkt nicht leer.
  • Die Erweiterungen-View hat verständliche Filter und keinen offensichtlichen Bug; der Eigenbau-Einstieg ist verlinkt.
  • Ein Skill wird in einem zentralen Tab (kein Popup) angelegt/bearbeitet; die Preview zeigt umschaltbar Skill-Datei und echten Laufzeit-Prompt.
  • /skills öffnet eine echte Übersicht (kein Toast); /neuer-skill öffnet einen leeren Editor-Tab.
  • In der „Werkstatt"-Sandbox lässt sich mit /erweiterung + /execute eine Beispiel-Erweiterung bauen, testen, herunterladen und wieder installieren; sie erscheint danach in der Erweiterungen-View.
  • Pro Sandbox lässt sich eine von drei Zugriffs-Stufen wählen; „voll" ist als Admin-Aktion markiert.
  • Ein geändertes Dokument mit weniger Chunks hinterlässt keine veralteten Treffer mehr (Zombie-Chunk-Test grün).
  • ./scripts/test/run-tests.sh --all ist grün; Doku (API/DB/ENV/WORKSPACE) synchron.
§6Verifikation auf dem Jetson ▶ Kurz: Jede Phase einzeln bauen, deployen und im echten Browser prüfen — nichts als „fertig" melden, was nicht live lief.

Verifikation läuft strikt phasenweise auf dem Gerät — nicht erst am Ende. Nach jeder Phase:

  1. docker compose up -d --build <service> für die berührten Dienste (Frontend, dashboard-backend, ggf. document-indexer).
  2. Erreichbarkeit + echte Browser-Prüfung unter https://192.168.0.197 (Login admin, Cert-Trust wie gehabt).
  3. Phasen-spezifische Sicht-Prüfung im Browser:
    • A/B: Switcher wechselt Kontext; Sidebar einklappen → „Dateien" bleibt erreichbar.
    • C: Modell-Filter links, ruhiges Grid, Detailseite gefüllt.
    • D: Skill-Tab öffnet ohne Popup; Live-Prompt-Ansicht zeigt echten Prompt.
    • E: Beispiel-Erweiterung in der Werkstatt bauen → /execute → Download → Install → erscheint in der View.
    • F: Dokument ändern (weniger Inhalt) → alte Treffer verschwinden aus der Suche.
  4. Backend-Verifies ohne Passwort via on-device JWT-Mint (siehe Memory) für API-Checks.

Was nicht live verifiziert werden konnte, wird als „blockiert/deviation" im Report vermerkt — nicht als erledigt.

Rollback

Jede Phase ist für sich revertierbar (eigener Branch/PR). DB-Migrationen sind additiv (neue Tabellen/Spalten, kein Drop) — ein Revert der App-Schicht lässt die Daten unberührt. Frontend-Store-Migrationen sind vorwärts-kompatibel; im Zweifel Store-Key zurücksetzen. Der Indexer-Umbau kann per Env-Flag deaktiviert werden, bis der Regressionstest grün ist.
