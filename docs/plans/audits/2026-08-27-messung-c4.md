## Die Entscheidungen dieser Phase

| Entscheidung                                               | Warum                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Eine Regel, zwei Stellen** (`appZugang.js`)              | Die Seite prüft Arasul selbst, das App-Backend prüft Traefik per Forward-Auth. Zwei Wege, aber eine Antwort: zwei Prüfungen wären zwei Orte, an denen dieselbe Frage falsch beantwortet werden kann.                                                                            |
| Das Etikett hängt am Container, nicht in `middlewares.yml` | Es trägt Kennung und Stand der App, und beides weiß nur, wer den Container anlegt. Eine Middleware in der statischen Datei müsste den Pfad aus `X-Forwarded-Uri` zerlegen — eine Stelle mehr, an der die Zuordnung schiefgeht.                                                  |
| `authResponseHeaders` ist die Fälschungssicherheit         | Traefik **löscht** jeden dort genannten Kopf aus der eingehenden Anfrage, bevor es ihn aus der Antwort der Anmeldung neu setzt. Ohne diese Liste wäre `X-Arasul-User` eine Zeile, die jeder Browser selbst schreiben kann.                                                      |
| **Seite 302, Schnittstelle 401**                           | Ein `fetch` der App bekäme auf einen Umzug die Anmeldeseite als HTML zurück und meldete einen Fehler, der nach einem Fehler der App aussieht — genau der Fall, vor dem `APPS.md` seit C3 warnt.                                                                                 |
| **Erst die Freigabe, dann die Existenz**                   | Wer eine App nicht freigegeben hat, erfährt auch nicht, ob es sie am Gerät gibt. Eine unbekannte App ist damit 403 statt 404; sonst wäre die App-Liste eines Unternehmens für jeden Angemeldeten abzählbar. Ändert eine Zeile der C3-Abnahme, mit Begründung an Ort und Stelle. |
| `/apps/<id>/api/me` gehört der Plattform                   | Der dritte vergebene Name unter `/apps/<id>/` und der einzige, der einer App etwas wegnimmt. Eine App darf ohne Backend auskommen; dann gäbe es sonst niemanden, der sagen könnte, wer angemeldet ist. `Path` statt `PathPrefix`: `/api/meine-antraege` bleibt der App.         |
| Der Name geht als UTF-8 über die Kopfzeile                 | Node prüft Kopfzeilen gegen `[\t\x20-\x7e\x80-\xff]` und wirft darüber. Ein Benutzer mit einem Namen jenseits von Latin-1 hätte JEDEN Aufruf an JEDE App mit einem 500 beendet. Steuerzeichen fallen weg, damit ein Zeilenumbruch im Namen keine zweite Kopfzeile wird.         |
| Keine Benutzernummer in den Kopfzeilen                     | Eine App, die Daten je Mensch ablegt, braucht einen stabilen Schlüssel — aber ein Feld, das die Plattform setzt und niemand liest, ist eine Zusage, die man später nicht mehr los wird. Wer sie braucht, bekommt sie in der Phase, die sie braucht.                             |
| Kein Zwischenspeicher über der Freigabe                    | Eine zurückgenommene Freigabe soll sofort wirken, nicht nach einer Minute. Der Preis ist eine indizierte Abfrage je Anfrage, auch je Stylesheet einer App.                                                                                                                      |
| **Je Stand ein Schlüssel**, nicht je App                   | Der Teststand ist eine andere Version, die jemand gerade ausprobiert. Landet sein Schlüssel in einem Protokoll, soll das den Livestand nichts kosten.                                                                                                                           |
| **Bei jedem Einspielen ein neuer**, kein zweiter Ablageort | In der Datenbank steht nur der bcrypt-Abdruck. Ihn daneben verschlüsselt abzulegen, um ihn später noch einmal in einen Container zu schreiben, wäre ein zweiter Ort mit einem gültigen Schlüssel — und gebraucht würde er nie, weil das Einspielen den Container ersetzt.       |
| Die Zeile in `apps` steht jetzt VOR dem Container          | Der Schlüssel hängt als Fremdschlüssel an ihr. Kommt der Container nicht hoch, wird sie wieder weggeräumt, aber nur, wenn dieser Aufruf sie angelegt hat — sonst belegte eine leere Zeile dauerhaft einen Platz der Lizenzgrenze.                                               |
| Das Image wird geholt, bevor der Schlüssel wechselt        | `starte` holt es ohnehin, aber erst danach. Ein Image, das nicht kommt, hätte einer laufenden App den Schlüssel unter den Füßen weggezogen.                                                                                                                                     |
| Die Migrationskette prüft **beide** Wege                   | Der Erstlauf (Docker-Init, `ON_ERROR_STOP=1`) und der Runner. 169 ist auf dem einen gescheitert und hätte auf dem anderen den Container gar nicht erst hochkommen lassen; nur beide zusammen sind der Vertrag aus `services/postgres/CLAUDE.md`.                                |

## Was die Abnahme misst

`scripts/test/app-anmeldung-abnahme.sh` gegen `https://localhost:8443`,
nachdem `scripts/test/beispielapp.sh einspielen` auf dem Gerät gelaufen ist.
Das Skript legt sich seine beiden Menschen selbst an und räumt sie am Ende weg,
auch wenn unterwegs etwas rot war.

1. **Der Freigegebene sieht seinen Namen.** `/apps/beispielapp/api/me` ist 200
   und nennt genau diesen Menschen samt Rolle; `/apps/beispielapp/` liefert ihm
   die Seite; `/apps/beispielapp/api/hallo` nennt denselben Namen aus
   `X-Arasul-User` — das erste beantwortet Arasul, das zweite das Backend der
   App aus dem Kopf, den es bekommen hat.
2. **Ein selbst mitgeschickter `X-Arasul-User: chef` kommt nicht durch.**
3. **Der API-Schlüssel steht in der Umgebung des Containers**, und die externe
   Schnittstelle nimmt ihn an (HTTP 200). Der Schlüssel selbst verlässt den
   Container nicht.
4. **Der Nicht-Freigegebene bekommt 403** auf Seite, `api/me` und `api/hallo`,
   und die Antwort ist eine Begründung als JSON, keine Seite. Der Administrator
   ohne Freigabe genauso: „Admins sehen alles" gibt es nicht.
5. **Ohne Sitzung** zieht die Seite auf `/` um (302), die Schnittstelle
   antwortet 401 ohne Umzug.
6. **Als Tester** wird aus dem 403 auf den Teststand ein 404 — der Unterschied
   belegt, dass die Freigabe vor der Existenz geprüft wird.
7. **Eine zurückgenommene Freigabe wirkt sofort.**

`scripts/test/migrationskette.sh` misst dazu, in der CI und von Hand: die
Initialisierung läuft durch, `168a` und `zzz` sind wirklich gelaufen, jede
Version steht im Buch, keine als gescheitert, keine Tabelle liegt doppelt in
`arasul` und `public` — und der Runner hat danach nichts mehr anzuwenden.

## Ein Fehler aus Migration 023, hier gefunden

`api_keys.key_prefix` ist seit 023 `VARCHAR(8)` („First 8 chars"), während
`middleware/apiKeyAuth.js` seit jeher zwölf Zeichen schreibt (`aras_` plus
sieben aus dem Zufallsteil). Postgres kürzt bei einem INSERT nicht, es weist
ab:

```
ERROR: value too long for type character varying(8)
```

`POST /api/v1/external/api-keys` scheitert damit am Gerät, und zwar seit 023.
Aufgefallen ist es hier, weil C4 der erste Weg ist, auf dem das Gerät **selbst**
einen Schlüssel anlegt. Migration 171 macht die Spalte auf 16 breit. Zeilen, die
noch da sind, tragen einen abgeschnittenen Präfix und waren ohnehin unbrauchbar
— die Suche vergleicht gegen zwölf; sie bleiben stehen, weil eine unbrauchbare
Zeile keinen Schaden anrichtet und ihr Löschen eine Entscheidung über fremde
Schlüssel wäre.

Ein Beleg dafür, dass der neue CI-Job zu eng gedacht ist, ist das **nicht**: er
prüft das Schema, nicht die Anwendung gegen das Schema. Was diesen Fall gefunden
hätte, wäre ein Test, der wirklich einen Schlüssel anlegt — den gibt es jetzt
(`apps.test.js`, „setzt einen frischen Schluessel in die Umgebung des
Containers"), allerdings gegen einen `pg`-Mock. Als Lücke notiert.

## Unterwegs gefunden, nicht Teil der Phase

- **`log_api_key_usage()` ruft niemand auf.** Die Funktion aus 023 füllt
  `api_key_usage`; im ganzen Repo gibt es keinen Aufrufer (nachgesehen am
  27.08.2026). Die Tabelle ist damit immer leer und steht trotzdem im
  Werksreset. Nicht angefasst: das wäre ein B3-Rückbau, keine C4-Aufgabe.
- **Ein Stand, der sein Backend verliert, behält seinen Schlüssel.** Spielt
  jemand eine Version ohne `backend` in einen Stand ein, in dem vorher eine mit
  Backend lief, wird kein Schlüssel erneuert und keiner zurückgezogen. Er passt
  dann noch zum alten Container — den C3 an dieser Stelle ebenfalls stehen
  lässt. Beide Hälften desselben Falls, und beide gehören zusammen behoben;
  einen davon allein aufzuräumen hieße, einen laufenden Container ohne
  Schlüssel zurückzulassen.
- **Die Abnahme-Reihe sitzt auf der Grenze der Anmeldedrossel.** Zwei für
  `rollen`, fünf für `mitarbeiter`, zwei für `app-anmeldung`, eine geteilte —
  genau zehn je Viertelstunde und IP. Die Rechnung steht jetzt in
  `anmeldung.sh`; die nächste Abnahme mit eigener Anmeldung sprengt sie.
- **Wer ohne Sitzung auf `/apps/<id>/` landet, verliert sein Ziel.** Der Umzug
  geht auf `/`, nicht auf `/?weiter=/apps/<id>/`. Ein Parameter, den die
  Oberfläche nicht auswertet, wäre toter Code; das gehört in die D-Phasen, die
  die Oberfläche ohnehin neu schneiden.
- **`GET /api/v1/external/llm/job/:jobId` antwortet immer 404.** Seit der
  Messung zu C2 offen, unverändert.
- **Der Letzter-Admin-Schutz prüft ohne Sperre.** Ebenfalls seit C2 offen.
- **`docs/api/DATABASE_SCHEMA.md` trägt weiter „Auto-generated. Do not edit by
  hand"** und wird weiter von Hand nachgezogen. Seit C2 offen.
- **Die Zahlen in `FEATURE_TIERS` sind gesetzt, nicht entschieden.** Seit C3
  offen; eine Preisentscheidung und damit Koljas.
